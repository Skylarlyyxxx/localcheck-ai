# LocalCheck AI 产品案例说明

## 一句话介绍

LocalCheck AI 是一个面向跨境独立站卖家的本地化准备度诊断 MVP：用户输入店铺 URL 并选择目标市场，即可获得一份基于公开首页信号的、可解释的本地化报告。

在线体验：[localcheck-ai.vercel.app](https://localcheck-ai.vercel.app/)

## 问题与产品假设

进入海外市场并不等于把页面翻译成另一种语言。货币、支付方式、退换货信息、信任内容、搜索基础信息和政策入口，都可能影响用户是否愿意继续浏览或下单。

本项目的产品假设是：在卖家投入完整本地化改版前，一份低门槛、可解释的首页诊断能够帮助其快速识别明显的市场适配缺口，并确定优先改进方向。

## MVP 用户流程

```text
输入 URL + 选择目标市场
          ↓
服务器抓取公开首页 HTML
          ↓
提取网页信号并匹配市场规则
          ↓
生成六维评分、证据与优先建议
```

当网站无法访问、超时或主动拦截分析时，产品会显示清晰提示，并保留 Demo Report 作为演示兜底。

## 核心设计取舍

### 先做规则，而不是直接接入 LLM

MVP 选择确定性规则检测：它成本低、结果可复现，且能直接展示“为什么得分”和“缺失什么”。这适合验证诊断需求是否存在，也避免在早期用黑盒结果掩盖规则本身的问题。

LLM 适合后续补充语言自然度、品牌表达和文化语境等难以靠关键词判断的内容，但目前**尚未接入线上诊断**。

### 只分析首页

首页的公开 HTML 足以完成第一版快速筛查，也能避免复杂爬虫、浏览器自动化和隐私风险。报告会明确提示：结账、商品页和动态加载内容不在本次范围内。

## 本地化框架

报告由六个维度组成：

| 维度 | 主要检查信号 |
| --- | --- |
| Currency | 目标市场货币代码与符号 |
| Payment | 当地常见支付方式的公开信号 |
| Trust & Conversion | 评论、配送、退换、联系、FAQ、安全支付 |
| SEO | Title、Description、H1、语言声明、Canonical |
| Legal & Policy Signals | 可发现的隐私、条款、退换和政策入口信号 |
| Language & Cultural Readiness | HTML 语言声明、目标语言文本、货币适配 |

美国、德国和日本拥有不同的货币、支付、语言和政策信号配置。因此同一个网站在三个市场下可能得到不同的结果。

## 报告可解释性

每个维度都会展示：

- **Detected Signals**：在公开首页检测到的信号
- **Missing Signals**：对应市场尚未检测到的信号
- **Why It Matters**：固定的产品解释

报告还分开展示：

- **Top Priorities**：Critical 与 Recommended 改进项
- **What You&apos;re Doing Well**：已检测到的良好实践

这样用户不只看到一个分数，也能理解下一步应先做什么。

## 工程实现

- Next.js App Router + TypeScript + Tailwind CSS
- Next.js Route Handler 在服务器端请求目标页面；浏览器不会直接请求第三方网站
- Cheerio 解析静态 HTML，不执行第三方 JavaScript
- 10 秒超时、仅首页、HTML 大小限制
- 基础 SSRF 防护：仅允许 HTTP(S)，拦截 localhost、私有 IP、内嵌认证信息与多次重定向风险
- 无数据库、登录、支付或付费 API

## 当前局限

- 关键词或 HTML 信号只能说明“检测到”，不代表支付真正可用，也不能判定法律合规。
- 强依赖客户端渲染、反爬或登录的网站可能无法分析。
- 只覆盖首页，不能代表完整站点体验。
- 德国、日本规则适合 MVP 对比与产品演示，不替代本地化专家或法律审查。

## 下一步路线图

1. 引入经过成本、稳定性和隐私验证的 LLM 语义分析，补充语言自然度与文化表达判断。
2. 扩展到产品页、购物车与结账前页面的多页审计。
3. 增加可选的持续监测与竞品基准能力。

## 面试讲解要点

> 我没有在 MVP 阶段先接入 LLM，而是优先做了可解释的规则诊断闭环。这样能先验证用户是否需要“按市场发现本地化缺口”，也能用真实网页测试评分是否合理。后续如果接入 LLM，我会让它处理语言自然度和文化语境等规则难以覆盖的部分，而不会替代确定性信号检测。
